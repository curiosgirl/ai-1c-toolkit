# Общий контракт субагентов

Обязателен для каждого субагента из каталога `agents/`. Субагент читает этот файл первым, затем свой файл `agents/onec-*.md`. Регламент применения субагентов и конвейеры - в `workflow/subagents.md`.

Субагент работает в чистом контексте: он не видит переписку пользователя с главным агентом. Все, что ему нужно, он получает из задания или читает из файлов репозитория.

---

## 1. Вход: что должно быть в задании

Главный агент передает в задании:

1. **Цель** - один вопрос или одна проверка, на которую нужен ответ.
2. **Объект работы** - пути к файлам и каталогам, либо ветка и базовая ветка для diff, либо путь к подготовленному worktree, либо текст отчета (для `onec-verifier`).
3. **Ограничения** - что исключить из проверки (например, «запросы не проверять, их проверяет `onec-query-auditor`»).

Параметры проекта (`{PREFIX}`, `{PLATFORM_VERSION}`, `{USES_BSP}`, `{LOCK_MODE}`, `{EDT_PROJECT_FORMAT}`) субагент читает сам из `project-profile.md`, а не берет из пересказа в задании. Если значение в задании расходится с профилем, действует профиль, расхождение фиксируется в отчете.

Если обязательных данных нет и их нельзя определить по файлам репозитория, субагент не выдумывает их, а возвращает отчет со статусом `BLOCKED` и списком недостающего.

## 2. Обязательное чтение

1. `project-profile.md` - параметры проекта.
2. `rules/project-context.md` - зоны кода и каталоги, которые не читаются.
3. Файлы правил и навыков, перечисленные в описании конкретного субагента. Остальные правила открываются только при необходимости: весь пакет «на всякий случай» не загружается.

## 3. Права и запреты

Разрешено:
- чтение и поиск по файлам репозитория;
- запуск скриптов из `skills/*/scripts/` без флагов исправления (`--fix` запрещен);
- команды Git только на чтение: `git diff`, `git log`, `git show`, `git status`, `git blame`;
- инструменты статического анализа в режиме анализа (BSL LS `analyze_file`, CLI `bsl-language-server analyze`).

Запрещено:
- изменять, создавать и удалять файлы репозитория;
- команды, меняющие состояние: `git checkout`, `git fetch`, `git reset`, `git stash`, `git commit`, `git push`, установка пакетов, обновление информационной базы;
- публиковать комментарии в MR/PR, одобрять (Approve) и сливать (Merge) их;
- запускать других субагентов: конвейеры собирает главный агент;
- читать каталоги из раздела «Что не читать и не править» файла `rules/project-context.md`.

Если для выполнения задачи нужно действие из списка запрещенных, субагент не выполняет его, а описывает в разделе «Вопросы» отчета.

## 4. Правила доказательности

1. **Каждый вывод опирается на прочитанный фрагмент или на вывод команды.** У вывода есть ссылка `путь:строка` или `путь:начало-конец` (путь от корня репозитория или worktree).
2. **Замечание сопровождается цитатой** - 1-5 строк кода, к которым оно относится. Цитата копируется из файла, а не воспроизводится по памяти.
3. **Факт отделяется от гипотезы.** Уверенность оценивается по шкале Confidence из `skills/bsl-code-review/SKILL.md` (раздел 3). Вывод с Confidence ниже 70% оформляется как вопрос, а не как дефект.
4. **«Не найдено» указывается только вместе со способом поиска:** где искали, каким шаблоном, сколько файлов просмотрено. Голое «проблем нет» не допускается.
5. **Правило называется ссылкой на файл**, а не пересказом: `rules/query-design.md`, раздел «...».
6. **Замена инструмента фиксируется.** Если MCP или скрипт недоступен, в отчете сказано, чем его заменили (например, ручной проверкой по чек-листу) и что из-за этого могло быть пропущено.
7. **Сторонний код не оценивается.** Замечания по зонам «сторонний функционал» и «фреймворк тестирования» не выставляются.

## 5. Формат отчета

Отчет возвращается одним сообщением в следующей структуре. Раздел «Выводы» заполняется в формате, заданном в описании конкретного субагента. Файлы целиком в отчет не вставляются.

````markdown
## Итог
Статус: DONE | PARTIAL | BLOCKED
{Одна-две фразы: главный результат.}

## Выводы
{В формате конкретного субагента. Каждый пункт - со ссылкой путь:строка и Confidence.}

## Что сделано
### Прочитанные файлы
- `путь` (строки N-M | целиком)

### Команды и поиски
- `команда или шаблон поиска` (где) -> результат: код возврата, число совпадений

## Что не проверено
- {Что именно} - {почему: нет инструмента, вне зоны, исключено заданием, динамический вызов, лимит объема}

## Вопросы
- {Что нужно уточнить у главного агента или пользователя. Пусто - написать «нет».}
````

## 6. Статусы

| Статус | Когда ставится |
|---|---|
| `DONE` | Весь объект работы проверен. Раздел «Что не проверено» может содержать только пункты, исключенные заданием или находящиеся вне зоны |
| `PARTIAL` | Часть объекта не проверена по причинам, перечисленным в разделе «Что не проверено» |
| `BLOCKED` | Работа не начата или прервана: не хватает входных данных или нужно запрещенное действие |

Раздел «Что не проверено» обязателен при любом статусе. Без него отчет нельзя отличить от отчета, в котором часть работы пропущена молча.
