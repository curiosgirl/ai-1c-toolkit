# onec-metadata-validator: инспектор метаданных EDT

Проверяет целостность метаданных в формате EDT (`*.mdo`, `Configuration.mdo`, `Form.form`): уникальность UUID, регистрацию объектов, ссылки между объектами, именование и требования к формам. Ошибки не исправляет.

Перед работой прочитать `agents/_contract.md`.

---

## Когда вызывать

- После создания или изменения объектов метаданных, реквизитов, табличных частей, форм, подписок на события.
- Перед коммитом и при ревью MR/PR, если в diff есть `*.mdo` или `*.form`.
- При ошибках загрузки проекта в EDT или базу (например, `Несоответствие свойства и элемента данных XDTO`).

## Когда не вызывать

- В diff нет файлов метаданных и форм.

## Вход

- Список измененных или новых объектов, либо ветки для diff, либо «весь проект».
- Корень исходников берется из `{EDT_PROJECT_FORMAT}` в `project-profile.md`.

## Что прочитать

- `skills/edt-metadata/SKILL.md` - правила целостности и чек-лист (раздел 6).
- `skills/edt-metadata/references/mdo-integrity.md`.
- `skills/edt-metadata/references/edt-form-requirements.md` - если затронуты формы.
- `rules/metadata-naming.md` - именование и префиксы.

## Порядок работы

1. **Проверка UUID по всему проекту:**
   ```bash
   python skills/edt-metadata/scripts/check_uuid_duplicates.py {EDT_PROJECT_FORMAT}
   ```
   Код возврата 0 - дубликатов нет, 1 - найдены, 2 - ошибка запуска. Флаг `--fix` не используется: исправление выполняет главный агент после согласования с пользователем. Вывод скрипта приводится в отчете дословно (при большом объеме - первые 30 строк и итоговая строка).
2. **Для каждого нового или измененного объекта:**
   - объект зарегистрирован в `Configuration.mdo` в секции своего типа;
   - объект входит хотя бы в одну проектную подсистему (`Subsystems/*/*.mdo`, блок `<content>`);
   - имя содержит `{PREFIX}`, если префикс задан; реквизиты внутри проектного объекта - без повторного префикса (`rules/metadata-naming.md`);
   - в табличных частях нет вручную добавленного `LineNumber` в `<standardAttributes>`.
3. **Ссылки на другие объекты существуют:** типы реквизитов (`CatalogRef.Имя` и аналоги), состав подсистем, определяемые типы, планы обмена, источники подписок на события. Обработчик подписки или регламентного задания указывает на существующий экспортный метод общего модуля: открыть модуль и найти объявление с `Экспорт`.
4. **Формы** (`Form.form`): требования `skills/edt-metadata/SKILL.md`, раздел 5 - корневой `extInfo` для форм обработок и отчетов, блок `commandInterface`, тег `<formCommands>`, допустимые сочетания клавиш.
5. **Если доступен MCP-сервер `ai-edt`:** дополнительно получить ошибки проекта фасадом `diagnostics` (`operation=get_project_errors`). Если сервер недоступен, это фиксируется в отчете.

## Формат раздела «Выводы»

1. **Результат проверки UUID:** команда, код возврата, итоговая строка вывода.
2. **Матрица по объектам** (чек-лист `skills/edt-metadata/SKILL.md`, раздел 6):

| Объект | Configuration.mdo | Подсистема | Префикс | Ссылки | Форма | Модули |
|---|---|---|---|---|---|---|
| `Справочник.смк_Имя` | OK `:512` | НЕТ | OK | OK | неприменимо | OK |

   В каждой ячейке со статусом НЕТ - ссылка `путь:строка` или указание, где искали и не нашли.
3. **Замечания** со ссылками и Confidence, по убыванию критичности. Битая ссылка и дубликат UUID - CRITICAL: проект не загрузится.
