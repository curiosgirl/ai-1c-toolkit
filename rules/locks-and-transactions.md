# Блокировки и транзакции: правила проектирования

Платформа 1С предлагает две подсистемы блокировок (автоматическую и управляемую) и модель неявных транзакций вокруг записи объектов. Большинство производственных инцидентов с блокировками происходит из-за смешивания двух режимов, открытия непреднамеренных транзакций или удержания блокировок во время диалогов с пользователем. Этот файл - канонический дом таких правил.

> **Область.** Файл владеет правилами проектирования. Узкий разобранный пример («установить блокировку до чтения остатков при проведении») лежит в `platform-solutions.md`, раздел «Управляемые блокировки и предотвращение взаимоблокировок», и ссылается сюда за общей теорией.

## 1. Режим блокировки конфигурации

Установить свойство конфигурации **«Режим управления блокировкой данных»** в значение `Управляемый` для всей конфигурации. Причины:

- Смешанный режим скрывает ошибки: код, написанный под автоматические блокировки, внезапно конфликтует, когда тот же путь данных выполняется в управляемом режиме.
- Управляемый режим - единственный, где гранулярность блокировок в руках разработчика (по таблице и ключу, а не по страницам строк).
- Современные подсистемы БСП предполагают управляемый режим.

Перевод существующего проекта с автоматического режима на управляемый - отдельная многошаговая задача и здесь не рассматривается; использовать материал ИТС «Перевод конфигурации на управляемый режим блокировки».

## 2. Границы транзакций

### Неявные транзакции

Платформа открывает собственную транзакцию вокруг:

- `Записать()` / `Записать(РежимЗаписиДокумента....)` ссылочного объекта - охватывает **`ПередЗаписью` → запись → `ПриЗаписи` → проведение (`ОбработкаПроведения`)**;
- `Удалить()` ссылочного объекта;
- `НаборЗаписей.Записать()` для наборов записей регистров;
- материализации движений в конце `ОбработкаПроведения`.

**Внутри `ПередЗаписью` / `ПриЗаписи` / `ОбработкаПроведения` объекта НЕ открывать собственные `НачалоТранзакции` / `ЗафиксироватьТранзакцию`.** Транзакция уже есть; вложенный вызов имитирует точку сохранения, но ломает корректный откат при ошибке во внешней транзакции. См. `platform-solutions.md`, раздел «Транзакции в обработчиках событий».

### Явные транзакции в вызывающем коде

Когда вызывающему коду нужно атомарно записать несколько объектов или совместить запись с правками регистров, транзакцию открывать там:

```bsl
НачалоТранзакции();

Попытка
	Документ.Записать(РежимЗаписиДокумента.Проведение);
	// ... дополнительные изменения ...
	ЗафиксироватьТранзакцию();
Исключение
	ОтменитьТранзакцию();

	ДанныеОшибки = Новый Структура;
	ДанныеОшибки.Вставить("Документ", Документ.Ссылка);
	ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));

	ЗаписьЖурналаРегистрации(
		"Проведение." + Документ.Метаданные().Имя + ".Ошибка",
		УровеньЖурналаРегистрации.Ошибка,
		Документ.Метаданные(),
		Документ.Ссылка,
		НСтр("ru = 'Не удалось провести документ.'"),
		ДанныеОшибки);

	ВызватьИсключение;
КонецПопытки;
```

Структурированные данные (`Данные = Структура`) и составное имя события следуют `logging-strategy.md` (разделы 3-5); контекст ошибки никогда не логировать одной склеенной строкой.

Правила:

- Форма `НачалоТранзакции()` → `Попытка` ... `ЗафиксироватьТранзакцию()` → `Исключение` `ОтменитьТранзакцию()` `ВызватьИсключение` `КонецПопытки` (см. пример выше) - **единственный правильный шаблон**. Любое отклонение (нет `Попытки`, нет `ОтменитьТранзакцию` в ветке исключения, нет повторного вызова исключения) - дефект.
- **Диагностировать, а не проглатывать.** Записать ошибку в журнал и сделать `ВызватьИсключение` - см. `logging-strategy.md`, раздел «Логирование ошибок и исключений».
- **Повторно проверять `ТранзакцияАктивна()`** перед вторым `ОтменитьТранзакцию` только в диагностике; обычно ход выполнения уже гарантирует это.

### Запрещено внутри транзакций

- **Диалоги с пользователем** (`ВопросАсинх`, `ПоказатьЗначение`, выбор файла). Любое ожидание ввода удерживает блокировки и стопорит другие сеансы.
- **Длительные операции** (`ДлительныеОперации`, сетевые вызовы, внешние компоненты). Выносить за пределы транзакции.
- **`ЗаписьЖурналаРегистрации` вместе с `Сообщить`** в клиентском контексте: сообщение уходит в интерфейс, заблокированный за транзакцией.

## 3. Примитивы управляемой блокировки

Блокировать управляемые данные через `БлокировкаДанных`:

```bsl
Блокировка = Новый БлокировкаДанных;

ЭлементБлокировки = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
ЭлементБлокировки.Режим = РежимБлокировкиДанных.Исключительный;
ЭлементБлокировки.ИсточникДанных = Товары;
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Склад",       "Склад");

Блокировка.Заблокировать();
```

Правила:

- **Блокировать до чтения**, затем читать, затем писать. Чтение без блокировки с последующей записью создает незащищенный промежуток, в котором параллельное проведение может записать несогласованные остатки.
- **Блокировать регистр**, а не документ. Блокировка документа не защищает регистр: следующее проведение все равно может прочитать устаревшие остатки.
- **`ИсточникДанных`**, а не ручной перебор. Всегда передавать табличную часть документа (или `ТаблицаЗначений`, построенную из нее) как `ИсточникДанных` и сопоставлять колонки через `ИспользоватьИзИсточникаДанных`; платформа скомпилирует один эффективный запрос блокировки.
- **Блокировка живет до конца текущей транзакции.** Раньше снять ее нельзя, можно только завершить транзакцию.

### Режимы

| `РежимБлокировкиДанных` | Когда использовать |
|---|---|
| `Исключительный` | Пути чтения-изменения-записи: проведение, массовая запись, перерасчеты. Блокирует и читателей, и писателей. |
| `Разделяемый` | Пути чтения, которые должны оставаться согласованными в рамках одной транзакции (например, отчет, читающий несколько регистров в одном снимке). Несколько разделяемых блокировок совместимы; исключительная блокировка против разделяемой ждет. |

По умолчанию `Исключительный` для любого пути записи. `Разделяемый` использовать осознанно: он не защищает от параллельных писателей, а лишь не дает им повыситься до исключительной блокировки, пока вы читаете.

## 4. Порядок блокировок - контракт против взаимоблокировок

Взаимоблокировка требует, чтобы две транзакции брали блокировки в разном порядке. Лечение - **зафиксировать порядок блокировок для всего проекта**.

Установить канонический порядок блокируемых таблиц и записать его в проектной документации (файл памяти проекта, вики или аналог) как проектное правило. Пример для иллюстративной операции по нескольким регистрам:

```
1. РегистрНакопления.ТоварыНаСкладах
2. РегистрНакопления.ТоварыКПередаче
3. РегистрНакопления.СвободныеОстатки
4. РегистрСведений.ЦеныНоменклатуры
5. РегистрНакопления.ВзаиморасчетыСКонтрагентами
```

В большой многодоменной конфигурации этот список - по домену: у каждой бизнес-области (например, склад, расчеты, закупки) должен быть свой документированный канонический порядок, а не один глобальный список.

Правила:

- Каждое проведение, затрагивающее более одного регистра из списка домена, блокирует их в указанном порядке. Без исключений.
- Новые регистры добавляются в порядок **в конец**, а не вставляются в середину (перенумерация ломает уже пройденные ревью).
- Межпроводочные операции (один документ проводит другой) наследуют тот же порядок: вызывающий код должен взять блокировки в каноническом порядке, а затем вызывать подчиненные операции.

Если под нагрузкой наблюдается взаимоблокировка, вопрос всегда не «как повторить попытку», а «какая транзакция взяла блокировки не по порядку». Чинить порядок; повторные попытки - лишь заплатка.

## 5. Паттерны блокировок

### Паттерн: проведение документа по нескольким регистрам

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

	// 1. Построить объект блокировки один раз, в каноническом порядке.
	Блокировка = Новый БлокировкаДанных;

	БлокТовары = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
	БлокТовары.Режим = РежимБлокировкиДанных.Исключительный;
	БлокТовары.ИсточникДанных = Товары;
	БлокТовары.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
	БлокТовары.ИспользоватьИзИсточникаДанных("Склад", "Склад");

	БлокВзаиморасчеты = Блокировка.Добавить("РегистрНакопления.ВзаиморасчетыСКонтрагентами");
	БлокВзаиморасчеты.Режим = РежимБлокировкиДанных.Исключительный;
	БлокВзаиморасчеты.УстановитьЗначение("Контрагент", Контрагент);

	Блокировка.Заблокировать();

	// 2. Прочитать остатки и проверить.
	// 3. Записать движения через Движения.X.Добавить / Записать = Истина.

КонецПроцедуры
```

### Паттерн: массовая операция по многим документам

Когда нужна атомарность между документами, управлять транзакцией в вызывающем коде, а не в каждом документе. Иначе оборачивать каждый документ в собственную транзакцию и продолжать при сбое (с логированием каждого сбоя): выбирать по бизнес-требованию.

Никогда не держать одну транзакцию на тысячи документов: эскалация блокировок и давление на журнал парализуют кластер.

### Паттерн: обновление статуса вне проведения

Для регистров сведений, используемых как журнал статусов (например, `СтатусыЗаказов`, `СтатусыИнтеграции`), использовать запись набора записей регистра с `НаборЗаписей.Заблокировать()` внутри явной транзакции:

```bsl
НачалоТранзакции();

Попытка

	НаборЗаписей = РегистрыСведений.СтатусыИнтеграции.СоздатьНаборЗаписей();
	НаборЗаписей.Отбор.Заказ.Установить(СсылкаЗаказа);
	НаборЗаписей.Заблокировать();
	НаборЗаписей.Прочитать();

	// ... изменить набор ...

	НаборЗаписей.Записать();
	ЗафиксироватьТранзакцию();

Исключение
	ОтменитьТранзакцию();
	ВызватьИсключение;
КонецПопытки;
```

`НаборЗаписей.Заблокировать()` - удобная форма управляемой блокировки в пределах отбора набора; использовать, когда смысл именно «сейчас перезапишу эти записи».

## 6. Диагностика конфликтов блокировок и взаимоблокировок

### Симптомы

- *«Конфликт блокировок при выполнении транзакции»* - эпизодический таймаут на регистре; причина: другая транзакция держит тот же ключ в несовместимом режиме дольше `MaxLockWait` (по умолчанию 20 с).
- *«Deadlock»* - две транзакции ждут друг друга; причина: нарушен порядок блокировок (раздел 4).
- *«Запись регистра не удалось получить»* при проведении - обычно конфликт блокировок на базовом регистре, а не на наборе записей регистра.

### Инструменты диагностики

- **Технологический журнал (`logcfg.xml`)** - включить события `TLOCK` и `TDEADLOCK` для проблемного регистра. Журнал показывает, кто что держит и что ждет. Это единственный авторитетный источник ответа на вопрос «какие две транзакции зашли во взаимоблокировку».
- **`ТранзакцияАктивна()`** - проверка живости текущей транзакции; полезна только для самопроверок, не для межсеансовой диагностики.
- **DMV MS SQL (только серверная информационная база)** - `sys.dm_tran_locks`, `sys.dm_os_waiting_tasks` для «живого» снимка, когда технологического журнала недостаточно.
- **Повторное проведение** - перепровести проблемный документ под отладчиком, чтобы зафиксировать точную последовательность вызовов блокировок.

Блокировки диагностировать методично: воспроизвести → выдвинуть гипотезу → поставить эксперимент → исправить, а не гадать и повторять попытки.
