# Контекст проекта: структура репозитория, зоны кода, тесты

**Когда открывать:** перед любой правкой в репозитории (чтобы понять принадлежность файла к зоне кода и применимые к нему правила), при написании и рефакторинге тестов, при выборе доступного синтаксиса платформы 1С.

Параметры проекта (префикс, платформа, БСП, режим блокировок) — в `../project-profile.md`.  
Эталонный пример заполнения для enterprise-проекта — в `project-context.example.md`.

## Карта репозитория

Структура исходников 1С (EDT) и вспомогательных каталогов проекта:

| Путь | Назначение |
|---|---|
| Определяется `{EDT_PROJECT_FORMAT}` | Основная конфигурация (обычно `src/cf/src`, `src/configuration` или корень репозитория). Файлы метаданных `*.mdo`, модули `*.bsl`, формы `*.xml`. Исключаемые родительские конфигурации поставщика (`Configuration/ParentConfigurations*`) находятся в `.gitignore` |
| Каталоги расширений (cfe) | Проектные расширения (например, `extensions/<имя>/src` или расширение тестов `yaxunit/src`). Имеют собственный режим совместимости |
| `tests/` / `features/` | Сценарии автоматизированного тестирования (Vanessa Automation `*.feature`, тесты YAxUnit) |
| `tools/` / `scripts/` / `ci/` | Конфигурация CI/CD-пайплайнов, скрипты сборки, раннеры тестов |
| `rules/`, `workflow/`, `project-profile.md`, `AGENTS.md` | Пакет стандартов и правил для ИИ-агентов |

Параметры подключения к Git-хостингу (URL репозитория, основная ветка разработки) и трекерам задач задаются в `workflow/` и локальном файле разработчика `workflow/local.md`.

## Зоны кода

Перед изменением или ревью любого файла агент обязан определить его зону по каталогу и префиксу объекта.

| Зона | Признак | Как работать |
|---|---|---|
| **Типовой код конфигурации** | Объекты без проектных префиксов в каталоге основной конфигурации | Править минимально, строго в пределах задачи (`rules/metadata-naming.md`). Массовый рефакторинг, переформатирование и переименование типовых переменных **запрещены** |
| **Доработанный проектный код** | Объекты с проектным префиксом `{PREFIX}` (или дополнительными префиксами проекта) | Полные правила разработки из `rules/`. Новые объекты, реквизиты и формы создавать с префиксом `{PREFIX}` (см. `../project-profile.md`) |
| **Присоединенный сторонний функционал** | Внешние библиотечные модули и подсистемы сторонних вендоров | **Не трогать без явного запроса пользователя.** Замечания линтеров и код-ревью по нему не заводить |
| **Фреймворк тестирования** | Библиотечный код тестовых движков (например, префикс `ЮТ` в YAxUnit, модули Vanessa Automation) | Сторонний код под открытыми лицензиями (Apache 2.0 / MIT / BSD). Не рефакторить, не форматировать под правила проекта. Лицензионные шапки не удалять |
| **Проектные тесты и подготовка данных** | Модули тестов проекта (в тестовом расширении или каталоге тестов) | Полные правила качества кода из `rules/` (с учетом специфики тестирования ниже). Новые тесты создавать по шаблонам проекта |

### Границы применения правил

- Правила применяются к **новому и изменяемому** коду в рамках текущей задачи. Существующие нарушения в унаследованном коде массово не исправляются.
- Неопределенные случаи (объект с незнакомым префиксом, объект без префикса, но не похожий на типовой вендорский) — **уточнить у пользователя**, а не классифицировать молча.

## Проверка метаданных

Имена объектов метаданных конфигурации и расширений, реквизитов, табличных частей и элементов форм не придумывать:

1. Через инструменты чтения метаданных окружения (MCP / плагины среды разработки), если они подключены.
2. По исходным файлам проекта EDT (дескрипторы метаданных `*.mdo`, `Configuration.mdo`).
3. Для платформенных типов и методов — по синтакс-помощнику платформы 1С или специализированным справочным инструментам.
4. Для существующего кода — через инструменты BSL Language Server (`definition`, `find_references`, `analyze_file`).

## Версии платформы и асинхронные методы (`Асинх` / `Ждать`)

Доступность современного асинхронного синтаксиса определяется режимом совместимости конкретного проекта или расширения:

| Режим совместимости | Ключевые слова `Асинх` / `Ждать` | Рекомендации |
|---|---|---|
| `>= 8.3.18` | **Доступны** | В клиентском коде использовать асинхронные конструкции (`Асинх`, `Ждать`, функции `*Асинх`) по правилам `rules/async-methods.md` |
| `< 8.3.18` | **Недоступны** | Использовать `ОписаниеОповещения` и методы обратного вызова (`ПоказатьВопрос()`, `ПоказатьПредупреждение()`, `НачатьПомещениеФайлов()`). Конструкции платформы новее режима совместимости не применять |

> **Критически важно для расширений:** расширение конфигурации может иметь собственный режим совместимости, отличный от основной конфигурации (например, режим совместимости расширения `8.3.10` при основной конфигурации `8.3.27`). В коде модулей такого расширения применение `Асинх` / `Ждать` приведет к синтаксической ошибке платформы. Всегда сверять режим совместимости расширения перед написанием клиентского кода.

## Тесты на YAxUnit

Если в проекте для модульного тестирования используется фреймворк YAxUnit (`{TEST_FRAMEWORKS}` содержит `YAxUnit`), соблюдать следующие правила организации и написания тестов.

### Регистрация тестов

Тесты регистрируются в экспортной процедуре `ИсполняемыеСценарии()` тестового модуля (область `#Область СлужебныйПрограммныйИнтерфейс`) через цепочку методов `ЮТтесты`:

```bsl
Процедура ИсполняемыеСценарии() Экспорт

	ИмяПодсистемы = "СкладскойУчет";
	ЮТтесты.ВТранзакции()
		.ДобавитьТестовыйНабор("РасчетСебестоимости", ИмяПодсистемы)
		.Тег("Интеграционные")
		.Перед("ПодготовитьДанные")
		.УдалениеТестовыхДанных()
		.После("ПослеВсехТестов")

	.ДобавитьТест("ПроверитьРасчетСуммыСписания", "Проверка корректности формулы списания")
		.СПараметрами(ПредопределенноеЗначение("Перечисление.ТипыОпераций.Списание"));

КонецПроцедуры
```

- `ВТранзакции()` — тест выполняется внутри отдельной транзакции, которая автоматически откатывается после завершения, обеспечивая изоляцию БД.
- `.УдалениеТестовыхДанных()` — удаление объектов, созданных набором данных.
- `.Тег(...)` — тегирование наборов тестов для фильтрации и группировки в раннере (например, по подсистемам или типам тестов).
- Методы, передаваемые в `.Перед(...)`, `.После(...)`, `.ДобавитьТест(...)` — экспортные процедуры этого же модуля.

### Подготовка данных

Данные для тестов создаются через специализированные общие модули-фабрики (генераторы данных), а не конструируются вручную с нуля в каждом тесте:

- Модули генерации документов (например, методы создания проведенных/непроведенных документов с заполнением шапки и табличных частей);
- Модули генерации справочников и классификаторов;
- Модули записи тестовых наборов регистров сведений и накопления;
- Модули генерации фиктивных значений (ИНН, КПП, номеров, дат).

Перед созданием нового кода подготовки данных проверить, нет ли уже подходящего метода в существующих тестовых модулях проекта. Если готового метода нет — добавлять его в соответствующий общий модуль подготовки данных, избегая дублирования.

Проверки (утверждения) выполняются через API фреймворка, например:
```bsl
ЮТест.ОжидаетЧто(ФактическоеЗначение, "Сумма списания рассчитана неверно")
	.Равно(ОжидаемоеЗначение);
```
Данные между методами `.Перед(...)`, тестами и `.После(...)` передаются через контекст набора: `ЮТест.КонтекстТестовогоНабора()`.

### Правила качества кода в тестах

Все стандарты разработки из `rules/` действуют для тестового кода без исключений:

- `Сообщить()`, тернарный оператор `?(...)`, сравнение булевых с `Истина` / `Ложь` в тестах **запрещены**;
- чтение реквизитов ссылок — через `ОбщегоНазначения.ЗначениеРеквизитаОбъекта*` (если `{USES_BSP} = Да`);
- блоки `Попытка...Исключение` вокруг операций с БД допустимы только с явным комментарием-обоснованием. Если тест проверяет генерацию исключительной ситуации, использовать утверждения фреймворка на перехват исключения (например, `ЮТест.ОжидаетЧто(...).ВызываетИсключение(...)`), а не пустую конструкцию `Попытка...Исключение`.

Лицензионные шапки (Apache 2.0 и др.) в существующих модулях сторонних библиотек сохраняются. В новых модулях проекта баннеры автор/дата/история запрещены (`rules/code-style.md`).

## Приемочные BDD-тесты на Vanessa Automation

Если в проекте используется Vanessa Automation (`{TEST_FRAMEWORKS}` содержит `Vanessa Automation`):
- Сценарии разрабатываются в каталоге `tests/` в формате файлов `.feature` (Gherkin, язык `#language: ru`).
- При написании сценариев обязательно использовать скилл `skills/vanessa-bdd/SKILL.md`: поиск шагов по базе 1569 шагов через `python skills/vanessa-bdd/scripts/search_steps.py`. Запрещено выдумывать собственные формулировки шагов.
- Перед сдачей сценария обязательна валидация через `python skills/vanessa-bdd/scripts/validate.py <путь-к-файлу.feature>`.

## Что не читать и не править

Служебные каталоги и генерируемые файлы, которые агент **не должен** читать без явного запроса и не должен использовать как образцы кода:

- `.scannerwork/`, `.sonar/` — временные кэши и артефакты статического анализатора SonarQube;
- `Configuration/ParentConfigurations*` — исходники родительских конфигураций поставщика;
- `tests/json/`, `allure-results/` — результаты и дампы выполнения автотестов;
- Служебные сгенерированные файлы исключений синтакс-контроля (например, `tools/syntax-check/exceptionFile.txt`);
- Локальные каталоги харнессов и IDE (`.metadata/`, `.idea/`, `.cursor/`, `.claude/`).
