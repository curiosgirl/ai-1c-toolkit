# Пример контекста проекта: структура репозитория, зоны кода, тесты (Шаблон)

> Данный файл является **эталонным примером** заполнения `rules/project-context.md` для реального enterprise-репозитория на базе 1С:ERP / отраслевого решения (EDT) с расширениями и тестовым фреймворком YAxUnit. При адаптации пакета под свой проект скопируйте нужные секции в `rules/project-context.md` и заполните значения для вашей конфигурации.

Параметры проекта (префикс, платформа) — в `../project-profile.md`.

## Зоны кода

Перед правкой определить зону по префиксу объекта и каталогу.

| Зона | Признак | Как работать |
|---|---|---|
| Типовой код ERP | Объекты без префиксов проекта в `src/cf/src` | Править минимально, только в пределах задачи (`metadata-naming.md`). Массовый рефакторинг и переформатирование запрещены |
| Наш код основной конфигурации | Префиксы `смк_`, `УСОERP_`, `анл` | Полные правила из `rules/`. Новые объекты создавать с `{PREFIX}` = `смк_` |
| Присоединенный сторонний функционал | Префикс `уат` (в том числе суффиксы `_проф`, `_уэ`) | **Не трогать без явного запроса пользователя.** Замечания BSL LS и ревью по нему не заводить |
| Фреймворк YAxUnit | Объекты с префиксом `ЮТ` в `yaxunit/src` | Чужой код под Apache 2.0. Не рефакторить, не форматировать, не править под правила проекта. Лицензионные шапки не удалять. Замечания BSL LS и ревью по нему не заводить |
| Наши тесты и подготовка данных | Объекты с префиксом `УСО_` в `yaxunit/src` | Полные правила из `rules/` (с оговорками ниже). Новые тестовые модули называть `УСО_...` |

Правила применяются к **новому и изменяемому** коду. Существующие нарушения (обращения к реквизитам через точку, `Попытка` и т.п.) массово не исправляются.

Неопределенные случаи (объект с незнакомым префиксом, объект без префикса, но явно не типовой) — уточнить у пользователя, а не выбирать зону молча.

## Проверка метаданных

Имена объектов основной конфигурации (`смк_*`, `Перечисления.смк_...`, реквизиты) не придумывать. Сверять:

1. Через MCP чтения метаданных: `list_metadata_objects`, `get_metadata_structure`.
2. Либо по исходникам `src/cf/src` (файлы `*.mdo`).

Для API платформы использовать синтакс-помощник и справку платформы, для кода — инструменты BSL Language Server (`definition`, `find_references`, `analyze_file`).

## Версии платформы и `Асинх` / `Ждать`

| Где | Режим совместимости | `Асинх` / `Ждать` |
|---|---|---|
| Основная конфигурация `src/cf/src` | `8.3.27` | Доступны, применять по `async-methods.md` |

Планируется ли повышать режим совместимости расширения — открытый вопрос к команде. Пока не повышен, действуют ограничения выше.

## Тесты на YAxUnit

Код тестов лежит в `yaxunit/src`, в общих модулях `УСО_*`. Ориентироваться на существующие модули (например, `УСО_ТестСкладскойУчет`).

### Регистрация тестов

Тесты регистрируются в экспортной процедуре `ИсполняемыеСценарии()` модуля (область `СлужебныйПрограммныйИнтерфейс`) через цепочку `ЮТтесты`:

```bsl
Процедура ИсполняемыеСценарии() Экспорт

	ИмяПродукта = "Название продукта";
	ЮТтесты.ВТранзакции()
		.ДобавитьТестовыйНабор("Название набора", ИмяПродукта)
		.Тег(УСО_ЮТ_КлиентСерверПереопределяемый.ТегИерархии(ИмяПродукта))
		.Перед("ПодготовитьДанные")
		.УдалениеТестовыхДанных()
		.После("ПослеВсехТестов")

	.ДобавитьТест("ПроверитьЧто", "Описание сценария")
		.СПараметрами(Перечисления.смк_Пример.Значение);

КонецПроцедуры
```

- `ВТранзакции()` — тесты выполняются в транзакции, которая откатывается.
- `.УдалениеТестовыхДанных()` — удаление данных, созданных набором.
- `.Тег(УСО_ЮТ_КлиентСерверПереопределяемый.ТегИерархии(...))` — тег иерархии, по которому тесты группируются в списке. Уровни иерархии (продукт, подсистема и т.д.) задавать через `ТегИерархии(Уровень1, Уровень2, ...)`.
- Методы, на которые ссылаются `.Перед(...)`, `.После(...)`, `.ДобавитьТест(...)` — процедуры того же модуля. Тестовые методы, вызываемые движком, должны быть экспортными.

### Подготовка данных

Данные для тестов создавать через общие модули подготовки, а не собирать вручную в каждом тесте:

- `УСО_ПодготовкаДанныхОбщиеДокументы` (например, `НовыйДокумент(ИмяДокумента, ДанныеШапки, ДанныеТабличныхЧастей, Проведен, ВернутьОбъект)`);
- `УСО_ПодготовкаДанныхОбщиеСправочники`;
- `УСО_ПодготовкаДанныхОбщиеРегистрыСведений`;
- `УСО_ПодготовкаФиктивныхЗначений`.

Перед написанием нового кода подготовки данных проверить, нет ли уже подходящего метода. Если нужного нет, добавлять в соответствующий общий модуль, а не дублировать в тесте.

Проверки (утверждения) — через API фреймворка, например `ЮТест.ОжидаетЧто(Значение, Сообщение).Равно(Ожидаемое)`, а не через `ВызватьИсключение` и `Сообщить()`. Данные между `.Перед(...)`, тестами и `.После(...)` передавать через `ЮТест.КонтекстТестовогоНабора()`.

### Правила кода в тестах

Все правила `rules/` действуют и для `УСО_*`. Смягчений нет. В частности:

- `Сообщить()`, тернарный оператор, сравнение булевых с `Истина` / `Ложь` в тестах запрещены;
- доступ к реквизитам ссылок — через `ОбщегоНазначения.ЗначениеРеквизитаОбъекта*`;
- `Попытка...Исключение` вокруг чтения и записи в БД — только с обоснованием (комментарием «почему»). Если тест проверяет, что действие завершается ошибкой, использовать утверждения фреймворка на исключение, а не ручную `Попытка`.

Если команда решит смягчить какие-то правила для тестового кода, зафиксировать решение в этом разделе явно, с пометкой `[Правило проекта - строже стандарта ИТС]`. Молча ослаблять правила нельзя.

Шапки Apache 2.0 в существующих модулях сохраняются. В новых модулях баннеры автор/дата/история запрещены (`rules/code-style.md`).

## Что не читать и не править

- `.scannerwork` (артефакты SonarQube);
- `src/cf/src/Configuration/ParentConfigurations*` (родительские конфигурации, в `.gitignore`);
- `tests/json` (данные раннеров);
- `tools/syntax-check/exceptionFile.txt` (генерируется, вручную не править).

Эти пути не читать без необходимости и не использовать как образец кода.
