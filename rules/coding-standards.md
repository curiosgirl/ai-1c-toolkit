# Стандарты кодирования (индекс)

Авторитетное содержание по стилю, именованию, комментариям, запросам, доступу к данным и производительности лежит в подробных файлах: `code-style.md`, `metadata-naming.md`, `architecture.md`, `module-structure.md`, `anti-patterns.md`, `platform-solutions.md`, `locks-and-transactions.md`, `logging-strategy.md`. Параметры проекта - в `../project-profile.md`. Формы: начинать с роутера `forms.md`. Запросы: начинать с `query-design.md`. Этот файл - индекс заголовков и ссылок. **Перед написанием или ревью кода открыть нужный подробный файл.**

## Запрещенные вызовы и конструкции (для всего проекта)

Единственный источник - `code-style.md`, раздел «Запрещенные вызовы и конструкции»: тернарный `?(...)`, `Выполнить()` / `Вычислить()`, зашитые учетные данные, `Сообщить()`, `ЗаписьЖурналаРегистрации()` без явной задачи, `Попытка ... Исключение` вокруг чтения и записи в БД, сравнение булевых с `Истина` / `Ложь`, Yoda-синтаксис. Запреты по именованию (венгерская нотация, имена из глобального контекста, магические числа, отрицательные имена булевых) и пометки `[Правило проекта - строже стандарта ИТС]` живут там же. Запрет `COMОбъект` - в `architecture.md`, раздел «Кроссплатформенность».

Списки здесь не дублировать: при изменении правила правится только файл-владелец.

## Комментарии

Предпочитать самодокументируемый код. Комментарий уместен только когда добавляет ценность: мотивация, нетривиальный алгоритм, ограничения и побочные эффекты, маркеры техдолга (`TODO No.<задача>: ...`), обходы платформы. Комментарии-пересказы кода и баннеры с автором и историей запрещены: историю хранит git. Примеры и правило проверки - `code-style.md`, раздел «Комментарии».

## Ревью после каждой правки

После любой правки выполнить внутреннее ревью по масштабу изменения. Быстрое исправление: корректность и граничные случаи измененного фрагмента (плюс блокировки и транзакции, если правка рядом с транзакционным кодом). Полноценная доработка: полный список - стиль, читаемость, корректность, граничные случаи, безопасность, конкурентность, блокировки, транзакции. Всегда учитывать, есть ли уже внешняя транзакция (например, транзакция записи объекта), прежде чем открывать новую. Полное описание - `code-style.md`, раздел «Внутреннее ревью после каждой правки».

## Переиспользование кода

Прежде чем писать новый код, проверить общие модули и модули менеджеров: возможно, нужный экспортный метод уже есть. Если в среде доступен поиск по коду и шаблонам, использовать его до написания.

Переиспользование распространяется и на саму платформу: когда задача требует специализированной возможности (криптография, численные методы, анализ данных, система взаимодействия и боты, интеграционная шина и очереди, полнотекстовый поиск, регулярные выражения), сначала проверить справку платформы и БСП, и только потом проектировать собственную реализацию. **Если подходящий механизм найден, строить на нем**, а не изобретать параллельный.

## Области модулей

Канонические имена областей - русские, в стиле БСП. Шаблоны по типам модулей (общий, объекта и менеджера, формы) - `module-structure.md`. Области внутри процедур и функций запрещены, псевдообласти через комментарии запрещены.

## Управляемые формы

Точка входа - `forms.md`. Дальше по его таблице:

| Задача | Открыть |
|---|---|
| Компоновка с нуля / не указано размещение | `form-patterns.md` |
| Создание или структурное изменение `Form.xml` | `forms-add.md` |
| Код модуля формы, обработчики событий, зарезервированные имена | `form-module.md` |
| Клиентский `Асинх` / `Ждать` | `async-methods.md` |

Весь набор «на всякий случай» не загружать.

## Запросы

Точка входа - `query-design.md`. Авторитетное оформление и жесткие запреты - `architecture.md`, раздел «Запросы». Кратко:

- Проверять метаданные до написания запроса.
- Запросов в цикле нет, вместо них пакетные запросы с временными таблицами (`ВТ_*`).
- Всегда параметры (`Запрос.УстановитьПараметр()`), никогда конкатенация строк.
- Всегда псевдонимы `КАК`. `ПЕРВЫЕ N`, когда нужна только часть данных.
- Виртуальные таблицы фильтровать параметрами, а не `ГДЕ`.
- Результат запроса - в промежуточной переменной (`РезультатЗапроса = Запрос.Выполнить();`), цепочки вызовов запрещены.

## Доступ к данным: реквизиты ссылок

Не обращаться к реквизитам ссылок через точку (`Контрагент.ИНН`). Использовать `ОбщегоНазначения.ЗначениеРеквизитаОбъекта` / `ЗначенияРеквизитовОбъекта` / `ЗначениеРеквизитаОбъектов` / `ЗначенияРеквизитовОбъектов`. **[Правило проекта - строже стандарта ИТС.]** Таблица методов и шаблоны кеширования - `architecture.md`, раздел «Доступ к данным: реквизиты ссылок».

## Производительность

Обязательный минимум (серверные массовые операции, запросы, привилегированный режим, кеширование, коллекции, транзакции, управляемые блокировки) - `architecture.md`, раздел «Производительность». Каталог антипаттернов с приоритетами - `anti-patterns.md`. Подводные камни платформы (длительные операции, временное хранилище, транзакции, взаимоблокировки, даты, поиск в коллекциях, внешние компоненты) - `platform-solutions.md`.

## Правила проекта строже стандарта ИТС

Часть правил намеренно **строже** официального стандарта ИТС. Каждое такое правило помечено **`[Правило проекта - строже стандарта ИТС]`**. Обсуждая такое правило с пользователем или при ревью:

- называть его **решением проекта**, а не требованием ИТС;
- при вопросе явно указывать отличие от стандарта ИТС;
- не ослаблять правило молча «под ИТС»: поднять вопрос и дать решить пользователю.
