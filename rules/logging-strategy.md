# Стратегия логирования

`code-style.md` (раздел «Запрещенные вызовы и конструкции») запрещает `ЗаписьЖурналаРегистрации` без явной задачи; `architecture.md` (раздел «Обработка ошибок») запрещает пустые `Попытка / Исключение`. Этот файл - **позитивное** дополнение: как логировать, когда логирование действительно требуется.

## 1. Когда логировать

| Сценарий | Логировать? | Примечания |
|---|---|---|
| Интеграции: исходящий запрос HTTP / SOAP / очередь | **Да** | Указывать endpoint, метод HTTP, код состояния, время ответа, идентификатор корреляции. Тело запроса не включать, если в нем персональные данные или учетные данные. |
| Интеграции: входящий webhook / регламентный обмен | **Да** | Источник, размер данных, принято / отклонено, причина ошибки. |
| Фоновые задания (`ДлительныеОперации`, `РегламентныеЗадания`) | **Да** | Старт / финиш, успех / сбой, ключевые параметры (обезличенные). Нужно, потому что у пользователя нет обратной связи в интерфейсе. |
| Ошибки проведения (`ОбработкаПроведения` → `Отказ = Истина`) | **Да** | Документ, организация, бизнес-причина; пользователь ошибку видел, но журнал - единственное место, где она сохраняется. |
| Откат транзакции | **Да** | Причина + ключ документа / операции. |
| Обычный CRUD по метаданным через интерфейс | **Нет** | Достаточно аудита на уровне платформы. |
| Необработанные исключения, пойманные внешним обработчиком | **Да** | Полное `ПодробноеПредставлениеОшибки(ИнформацияОбОшибке())`. |
| Трассировочный / отладочный вывод при разработке | **Нет** | Использовать отладчик / `ПоказатьЗначение`; убрать перед коммитом. |

Практическое правило: **логировать то, что нельзя восстановить позже**. Ошибки, которые видят пользователи, границы интеграций, фоновая работа. Не логировать обычные чтения и записи, которые и так оставляют след в метаданных.

## 2. Уровни важности

`УровеньЖурналаРегистрации` имеет четыре значения; считать их контрактом:

| Уровень | Для чего |
|---|---|
| `Ошибка` | Операция не удалась, система в несогласованном состоянии или ожидает разбора. Уходит в мониторинг. |
| `Предупреждение` | Операция успешна по деградированному пути (повтор удался, использован запасной вариант, необязательная зависимость недоступна). Не поднимает дежурного, но попадает в сводные отчеты. |
| `Информация` | Значимое для бизнеса успешное событие: завершенная интеграция, завершенное фоновое задание, важное для аудита изменение состояния. |
| `Примечание` | Диагностические детали; в производственных путях кода применяется редко. Лучше не писать, чем создавать шум. |

Сопоставлять с уровнем вашего мониторинга (Zabbix / ELK / Prometheus): обычно `Ошибка` → оповещение, `Предупреждение` → сводка, остальное → только поиск.

## 3. Именование категорий событий

События `ЖурналРегистрации` фильтруются по категории (имени события). Использовать единообразное иерархическое имя через точку, чтобы `ОтборЖурналаРегистрации` работал предсказуемо:

```
<Подсистема>.<Операция>.<Результат>
```

Примеры:

- `Интеграция.ОбменСCRM.Запрос`
- `Интеграция.ОбменСCRM.Ответ`
- `Интеграция.ОбменСCRM.Ошибка`
- `Проведение.РеализацияТоваровУслуг.КонфликтБлокировки`
- `ФоновоеЗадание.ОбновлениеКурсовВалют.Старт`
- `ФоновоеЗадание.ОбновлениеКурсовВалют.Финиш`

В многодоменной конфигурации `<Подсистема>` должна быть конкретной бизнес-областью или модулем, к которому относится событие (например, префикс соответствующей подсистемы), а не общим «на все случаи»: так фильтры `ОтборЖурналаРегистрации` остаются пригодными для большого журнала.

Зарезервированный префикс `Debug.*` - **только** на время активной отладки, перед коммитом обязательно удалить. Никогда не отправлять `Debug.*` в производственную среду.

## 4. Структурированные данные

Когда у события есть контекстные поля, передавать `Структуру` в аргумент `Данные` метода `ЗаписьЖурналаРегистрации`. Склеенные строковые данные не разбираются downstream-инструментами.

В примере предполагается, что `ОрганизацияДокумента` уже доступна в вызывающем контексте. Не обращаться к `СсылкаДокумента` только ради построения данных журнала.

```bsl
ДанныеСобытия = Новый Структура;
ДанныеСобытия.Вставить("Документ", СсылкаДокумента);
ДанныеСобытия.Вставить("Организация", ОрганизацияДокумента);
ДанныеСобытия.Вставить("Длительность_мс", Длительность);
ДанныеСобытия.Вставить("HTTPСтатус", ОтветHTTP.КодСостояния);

ЗаписьЖурналаРегистрации(
	"Интеграция.ОбменСCRM.Ответ",
	УровеньЖурналаРегистрации.Информация,
	Метаданные.Документы.РеализацияТоваровУслуг,
	СсылкаДокумента,
	"",
	ДанныеСобытия);
```

Поля:

- **`ИмяСобытия`** - категория через точку из раздела 3.
- **`Уровень`** - из раздела 2.
- **`Метаданные`** - объект метаданных, к жизненному циклу которого относится событие. Передавать для событий проведения и записи; опускать (`Неопределено`) для сквозных событий вроде жизненного цикла регламентного задания.
- **`ДанныеИсточник`** - конкретная ссылка (документ, элемент справочника). Позволяет `ОтборЖурналаРегистрации` отфильтровать по одной сущности в один клик.
- **`Комментарий`** - краткий свободный текст. Пустая строка, когда `ДанныеСобытия` уже несет все.
- **`Данные`** - `Структура`. Движок сериализует ее через XDTO, и внешние разборщики читают отдельные поля.

## 5. Логирование ошибок и исключений

Внутри оправданного блока `Попытка / Исключение` (например, управление транзакцией, граница интеграции) ошибку нужно записать **один раз** с полным описанием:

```bsl
Попытка
	ВыполнитьИнтеграционныйЗапрос();
Исключение

	ДанныеОшибки = Новый Структура;
	ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	ДанныеОшибки.Вставить("Запрос", СтрокаЗапроса);

	ЗаписьЖурналаРегистрации(
		"Интеграция.ОбменСCRM.Ошибка",
		УровеньЖурналаРегистрации.Ошибка,
		,
		,
		"Не удалось выполнить запрос к CRM.",
		ДанныеОшибки);

	ВызватьИсключение;

КонецПопытки;
```

Правила:

- **`ПодробноеПредставлениеОшибки(ИнформацияОбОшибке())`**, а не `КраткоеПредставлениеОшибки()`: краткое представление теряет стек и причину.
- **Всегда пробрасывать исключение после логирования на границе интеграции**, если контракт не «проглатывать именно этот код ошибки». Молчаливое «залогировали и пошли дальше» - самая частая причина фантомных рассогласований данных.
- **Не логировать дважды.** Если внутренний обработчик уже записал запись уровня `Ошибка`, внешний пишет не выше `Предупреждение` («операция прервана из-за <внутренняя причина>») и не выгружает повторно то же `Подробно`.

## 6. Что НЕЛЬЗЯ писать в журнал

- **Учетные данные**: пароли, токены, ключи API, секреты OAuth, cookie сеансов, даже в `Подробно`. Всегда затирать перед записью.
- **Персональные данные на уровне тела запроса**: полные паспорт / СНИЛС / платежные карты / списки email. Писать хеш или идентификатор записи, а не само значение. Является ли поле персональным, зависит от классификации данных в проекте; при сомнении не писать.
- **Большие блоки данных и вложения.** Писать метаданные (размер, тип содержимого, идентификатор хранилища), а не байты.
- **Всю `ТаблицаЗначений`.** Писать сводку (`КоличествоСтрок`, ключевые колонки), а не всю таблицу.

Проектные классификации персональных данных, влияющие на логирование, фиксировать в проектной документации.

## 7. Ротация и хранение

- **`ЖурналРегистрации` по умолчанию не ограничен.** Настроить ротацию средствами конфигуратора (`Администрирование → Журнал регистрации → Настройки`). Для высоконагруженных систем задать период разделения (периодически вызывать `СократитьЖурналРегистрации` регламентным заданием) и архивировать старые срезы.
- **Выгрузка за пределы хоста.** В проектах с инфраструктурой мониторинга периодически выгружать через `ВыгрузитьЖурналРегистрации` во внешний приемник (ELK, Splunk, Kafka) и затем очищать журнал на стороне платформы. Потоковый «tail» в реальном времени платформа не поддерживает: если нужна потоковая телеметрия, использовать технологический журнал.
