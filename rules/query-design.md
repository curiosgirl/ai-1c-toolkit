# Проектирование запросов: точка входа

Этот файл - **роутер** для работы с запросами. Открывать первым, затем загружать только те источники, которые выбирает таблица ниже.

> **Область.** Файл отвечает за маршрутизацию и порядок чтения. Авторитетные жесткие правила (оформление, псевдонимы, параметры, запреты) - в `architecture.md`, раздел «Запросы». Каталог приоритетов и шаблоны исправлений - `anti-patterns.md`.

## Маршрутизация

| Задача | Открыть |
|---|---|
| Жесткие правила проекта (оформление, `КАК`, параметры, запросы в цикле, промежуточная переменная результата, фильтры виртуальных таблиц) | `architecture.md`, раздел «Запросы» |
| Антипаттерны и приоритеты (запрос в цикле, коррелированный подзапрос, фильтр виртуальной таблицы в `ГДЕ`, отсутствие `ПЕРВЫЕ N`, непроиндексированная временная таблица, лишний `РАЗЛИЧНЫЕ`, пакет с временной таблицей) | `anti-patterns.md` (§1, §3a, §4, §5, §5a, §7b, «Оптимизированные паттерны» - «Пакетный запрос с временной таблицей») |
| Блокировки и транзакции вокруг запроса и записи | `locks-and-transactions.md` |

Каждый файл самодостаточен: загружать только подходящие задаче. Весь набор «на всякий случай» не читать.

## Перед началом (каждый нетривиальный запрос)

1. **Проверить метаданные** до первого `ВЫБРАТЬ`. Не придумывать имена реквизитов и табличных частей. Если в среде есть поиск по метаданным, использовать его, иначе читать описание объекта в исходниках конфигурации.
2. **Найти проверенный образец.** Прежде чем изобретать новый каркас, поискать похожие запросы в кодовой базе и шаблонах. Если подходящий шаблон найден - брать его за основу и адаптировать только нужное.
3. **Выбрать правильный источник:** справочник / документ / срез регистра сведений / виртуальная таблица регистра накопления (`Остатки`, `Обороты`, `ОстаткиИОбороты`). Неправильный источник - дефект проектирования, а не проблема тюнинга.
4. **Применить жесткие запреты** из `architecture.md`, раздел «Запросы»: нет запросов в циклах, всегда параметры, всегда `КАК`, фильтры виртуальных таблиц через параметры (не `ГДЕ`), промежуточная переменная для `Запрос.Выполнить()`.
5. **Чек-лист по временным таблицам и объединениям** для каждого многопакетного запроса перед сдачей:
   - каждая временная таблица, позже используемая в `СОЕДИНЕНИИ` / `ОБЪЕДИНИТЬ` / `В (ВЫБРАТЬ ...)`, имеет `ИНДЕКСИРОВАТЬ ПО` по ключам соединения (2-3 наиболее селективных поля, а не весь список);
   - нет `РАЗЛИЧНЫЕ` внутри операндов `ОБЪЕДИНИТЬ` и поверх `СГРУППИРОВАТЬ ПО`;
   - коррелированные подзапросы заменены проиндексированной временной таблицей и соединением;
   - периодичность виртуальной таблицы соответствует ключам соединения.
6. **Проверить готовый текст.** Если в среде есть возможность проверить синтаксис запроса на тестовой базе, прогнать каждый текст запроса до попадания в модуль или схему СКД. Особенно после генерации или автоматического рефакторинга кода: это самый дешевый способ поймать ошибки, которых не видит проверка синтаксиса модуля внутри строки запроса.

## Рекомендуемый порядок чтения

```
query-design.md (этот файл)
  → architecture.md, раздел «Запросы»   # жесткие правила
  → anti-patterns.md                    # только при ревью или исправлении
```

## Вне области

- XML метаданных регистров и документов.
- Паттерны загрузки данных в модуле формы - `forms.md` → `form-module.md`.
- Границы блокировок и транзакций вокруг запроса и записи - `locks-and-transactions.md`.
- В этот пакет не входят отдельные руководства по написанию и оптимизации запросов и по запросам СКД. При необходимости добавьте их в `rules/` и пропишите в таблице маршрутизации.
