# Стандарты разработки: стиль кода BSL

**Когда открывать:** перед написанием или ревью BSL, когда важны оформление, именование, запрещенные конструкции, лимиты качества, документирование экспортных методов, типографика, качество комментариев или базовое внутреннее ревью.

## Оформление и стиль кода (единственный источник)

### Форматирование

- **Отступ:** только табуляция (не пробелы).
- **Длина строки:** не более 120 символов, если строку можно корректно перенести. Не вводить перенос, после которого на новой строке остается одна переменная.
- **Одна инструкция на строку.** Однострочные конструкции со сложной логикой запрещены.
- В условиях и циклах добавлять пустые строки до и после кода внутри блока для читаемости.
- Учитывать рекомендации линтера и BSL Language Server. Точечное и обоснованное подавление - комментарием `//BSLLS:`.

### Выравнивание

- Для групп однотипных присваиваний **в локальные переменные** выравнивать `=` пробелами.
- **Не выравнивать** при установке свойств объекта через точку: один пробел вокруг `=`.

### Метрики качества

| Метрика | Лимит | Строгость |
|---|---|---|
| Длина метода | не более 200 строк (исключение: тексты запросов) | жесткий лимит |
| Длина метода | более 100 строк - кандидат на декомпозицию | повод для ревью |
| Вложенность управляющих конструкций | менее 5 уровней | жесткий лимит |
| Когнитивная сложность | менее 15 | повод для ревью |
| Параметры метода | не более 5 (дополнительные - структурой шестым параметром) | жесткий лимит |

### Построение строк

Для составления строк использовать `СтрШаблон()`, а **не** конкатенацию через `+`.
Исключение: простое `Префикс + Суффикс` допустимо, когда так читается лучше.

### Запрещенные вызовы и конструкции

- `Попытка ... Исключение` вокруг чтения и записи в БД **ЗАПРЕЩЕНА**, кроме явного и обоснованного управления транзакцией.
- `ЗаписьЖурналаРегистрации()` **ЗАПРЕЩЕНА**, если это явно не требуется задачей.
- `Сообщить()` для уведомлений пользователя **ЗАПРЕЩЕНА**. Использовать `ОбщегоНазначения.СообщитьПользователю` (сервер) / `ОбщегоНазначенияКлиент.СообщитьПользователю` (клиент).
- `Выполнить()` и `Вычислить()` **ЗАПРЕЩЕНЫ** без крайней необходимости (см. `architecture.md`, раздел «Безопасность»).
- Зашитые в код учетные данные (пароли, токены, ключи API) **ЗАПРЕЩЕНЫ**.
- Тернарный оператор `?(Условие, Значение1, Значение2)` **ЗАПРЕЩЕН в любом виде**, включая простой невложенный случай. Использовать `Если ... Иначе` или вынести небольшую вспомогательную функцию. Обоснование: логика остается видимой в пошаговой отладке и при ревью. **[Правило проекта - строже стандарта ИТС.]**
- Сравнение булевых значений с `Истина` / `Ложь` запрещено: использовать булево выражение напрямую.
- Yoda-синтаксис (`Если 0 = Сумма`) **ЗАПРЕЩЕН**.

### Именование

- **Имена переменных отражают бизнес-смысл и роль.** Суффиксы типа допустимы только когда снимают неоднозначность и не превращаются в венгерскую нотацию.
- Венгерская нотация (`МассивКонтрагентов`, `ТаблицаДанных`) **ЗАПРЕЩЕНА**: использовать бизнес-имя (`Контрагенты`, `Данные`).
- Имена из глобального контекста 1С (`Документы`, `Справочники`, `Пользователи`, `Регистры`, `Метаданные`, `Константы` и т.п.) **НЕЛЬЗЯ** использовать как локальные переменные: они вызывают коллизии имен и ухудшают читаемость.
- Префикс `Получить*` в именах функций нежелателен, когда возвращаемое значение очевидно из имени или функция возвращает коллекцию (`Контрагенты()`, а не `ПолучитьКонтрагентов()`). Допустим при прямом делегировании вызову платформы или при реализации контракта API, совместимого с БСП.
- **Булевы переменные - только положительные имена** (`ПроверкаПройдена`, а не `ПроверкаНеПройдена`).
- **«Магические числа» ЗАПРЕЩЕНЫ**: выносить в именованные переменные или константы.
- **Перечисления строковых значений** - в алфавитном порядке.

### Условия

- Сложные условия (3 и более конструкций) выносить в отдельный метод.

### Параметры функций

- Параметр функции **НЕЛЬЗЯ** использовать как дополнительный выход: весь результат - через возвращаемое значение.
- Для дополнительных параметров использовать функцию-конструктор:

```bsl
Функция ПараметрыЗаполнения() Экспорт
	Параметры = Новый Структура;
	Параметры.Вставить("Дата");
	Параметры.Вставить("Валюта");
	Параметры.Вставить("ПересчитыватьСумму", Истина);
	Возврат Параметры;
КонецФункции
```

## Документирование процедур и функций

Обязательно для всех `Экспорт` процедур и функций (кроме предопределенных обработчиков):

```bsl
// Возвращает спецодежду для должности на указанную дату.
//
// Параметры:
//  ДатаДействия - Дата
//  Должность - СправочникСсылка.Должности
//
// Возвращаемое значение:
//  СправочникСсылка.{PREFIX}СпецодеждаДляДолжностей
//
Функция АктуальнаяСпецодеждаДляДолжности(ДатаДействия, Должность) Экспорт
```

- Описание начинается с глагола: «Возвращает...», «Проверяет...», «Рассчитывает...».
- **Не** начинать с «Процедура...», «Функция...» или имени функции.
- Для параметров-структур описывать ключи через `*`.
- Для массивов указывать тип элементов.

## Типографика

Эти правила относятся только к артефактам кода 1С: модули, комментарии в модулях, идентификаторы, строковые литералы, синонимы и представления метаданных, сообщения пользователю. Markdown-файлы проекта и документация правил вне области действия.

- **Не использовать букву «ё»** в коде 1С и пользовательских текстах конфигурации. Заменять на «е» в комментариях модулей, синонимах метаданных, представлениях и сообщениях. Причина: разная раскладка у команды и в базовых конфигурациях ломает текстовый поиск.
- **Не использовать длинное тире** `—`. Заменять дефисом `-`. Причина: несовпадение кодировок в стеке 1С (особенно в журнале регистрации и логах платформы) превращает тире в `?`.
- В пользовательских текстах использовать кавычки-«елочки» `«...»`. В строковых литералах кода - обычные `"..."`.
- Не использовать неразрывные пробелы и другие невидимые символы Unicode в коде.

## Комментарии: примеры «можно» и «нельзя»

Цель: убрать шум и оставить только полезные комментарии. Заголовочное правило - `coding-standards.md`, раздел «Комментарии».

### Нельзя: пересказ кода и шум

```bsl
// Получаем массив контрагентов
Контрагенты = ПолучитьКонтрагентов();

// Цикл по строкам таблицы
Для Каждого Строка Из Таблица Цикл

// Возвращаем результат
Возврат Результат;
```

```bsl
//////////////////////////////////////////////////////////////////
// Модуль: ОбщегоНазначения
// Автор: Иванов И.И.
// Дата: 15.03.2024
// Описание: Общие функции
// История изменений:
//   15.03.2024 - добавлено
//   17.03.2024 - исправлено
//////////////////////////////////////////////////////////////////
```

Декоративные баннеры `///` и заголовки модулей с авторством и историей изменений запрещены: это уже фиксирует git.

### Можно: мотивация, контекст, ограничения

```bsl
// НДС не начисляется при экспорте, см. ст. 164 НК РФ
Если Контрагент.Резидент И Не Документ.Экспорт Тогда

// Кеш используется потому, что метод вызывается ~10000 раз при проведении
// крупных накладных и каждый вызов делает запрос к регистру цен.
ИндексЦен = Новый Соответствие;

// Хак: платформа 8.3.23 не возвращает корректный тип в РазделительИБ
// при первом вызове после старта сеанса - повторяем запрос один раз.
Тип = Метаданные.ОбщиеРеквизиты.РазделительИБ.Тип;
Если Тип.Типы().Количество() = 0 Тогда
	Тип = Метаданные.ОбщиеРеквизиты.РазделительИБ.Тип;
КонецЕсли;

// TODO No.14752: после миграции на платформу 8.3.25 убрать обходной путь.
```

### Правило проверки

Перед тем как оставить комментарий, ответить: **«Что этот комментарий сообщает читателю такого, чего не говорит сам код?»** Если ответ «ничего» - удалить комментарий.

## Внутреннее ревью после каждой правки

После любой правки кода выполнить краткое внутреннее ревью, масштабируя его по пути:

- **Быстрое исправление** - корректность и граничные случаи измененного фрагмента, плюс блокировки и транзакции, если правка рядом с транзакционным кодом. Этого достаточно: полный чек-лист на правке в 10 строк не гонять.
- **Полноценная доработка** - полный список: стиль, читаемость, корректность, граничные случаи, безопасность, конкурентность, блокировки, транзакции, соответствие диагностикам BSL Language Server.

Если найдены проблемы, исправить и повторить проверку на измененном состоянии. Блокирующий дефект требует чистого подтверждающего прогона после исправления. Замечания только по стилю не запускают новый цикл проверок. Если после исправления блокирующего дефекта чистого прогона добиться не удалось, не объявлять проверку пройденной, а сообщить, что результат не подтвержден.

Всегда учитывать, есть ли уже внешняя транзакция (например, транзакция записи объекта), прежде чем открывать новую. Канонические шаблоны - `platform-solutions.md`.
