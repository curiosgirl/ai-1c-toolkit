# Регламент работы с субагентами

Документ определяет, когда главный агент делегирует работу субагентам, как составлять для них задания, как собирать из них конвейеры и как проверять их результат.

Субагент - отдельный экземпляр агента, который запускает главный агент. Он работает в чистом контексте, читает файлы и запускает инструменты сам, а главному агенту возвращает только итоговый отчет. Это экономит контекст основного диалога и позволяет выполнять независимые проверки параллельно.

---

## 1. Когда делегировать

Задача подходит для субагента, если выполнены все три условия:

1. **Широкий вход, узкий выход:** нужно прочитать много файлов, а вернуть короткую выжимку.
2. **Не нужен контекст диалога:** все необходимое помещается в задание или читается из репозитория.
3. **Результат проверяем:** у выводов есть ссылки `файл:строка`, вывод скрипта или пункт чек-листа.

Не делегировать:
- правку из нескольких строк и чтение 1-3 известных файлов - главный агент сделает это быстрее;
- проектирование, которое требует обсуждения с пользователем (раскладка формы, выбор архитектуры);
- ведение журнала и ADR (`skills/worklog-tracker/SKILL.md`) - им нужна история текущей сессии, которой у субагента нет;
- любые изменения файлов: все субагенты пакета работают только на чтение, правки вносит главный агент.

## 2. Состав

| Субагент | Назначение | Опора на детерминированный инструмент |
|---|---|---|
| `onec-explorer` | Карта вызовов, мест использования, подписок и перехватов в расширениях | Поиск по исходникам с перечнем шаблонов |
| `onec-reviewer` | Код-ревью diff по `workflow/code-review.md` | BSL Language Server (MCP или CLI), `git diff`, роль `platform-docs` для версий методов платформы |
| `onec-query-auditor` | Аудит запросов по `skills/query-optimizer/SKILL.md` | Сверка имен с `*.mdo` |
| `onec-metadata-validator` | Целостность метаданных EDT | `check_uuid_duplicates.py`, MCP `ai-edt` |
| `onec-bsp-checker` | Проверка вызовов БСП | `bsp-api.py check` / `show` |
| `onec-verifier` | Независимая перепроверка отчетов остальных субагентов | Повтор команд из проверяемого отчета |

Общие для всех правила - права, требования к доказательствам, формат отчета и статусы - в `agents/_contract.md`.

## 3. Как устроены файлы

```text
agents/                      # источник правды, нейтрален к харнессу
├── _contract.md             # общий контракт
└── onec-*.md                # роль, вход, порядок работы, формат выводов
.cursor/agents/onec-*.md     # адаптер Cursor
.claude/agents/onec-*.md     # адаптер Claude Code
```

Адаптер содержит только заголовок (имя, описание, ограничения) и указание прочитать `agents/_contract.md` и свой файл в `agents/`. Инструкции хранятся в одном месте, адаптеры не дублируют их.

| Харнесс | Откуда загружает | Ограничение прав |
|---|---|---|
| Cursor | `.cursor/agents/`, а также `.claude/agents/`. При совпадении имен приоритет у `.cursor/agents/` | `readonly: true` у всех субагентов: правка файлов и команды, меняющие состояние, заблокированы средой |
| Claude Code | `.claude/agents/` | `tools: Read, Grep, Glob, Bash` у `onec-query-auditor`, `onec-bsp-checker`, `onec-verifier`. Остальным нужны MCP-серверы (метаданные, BSL LS, справка платформы, `ai-edt`), поэтому список инструментов не ограничен, а запреты действуют через контракт |
| Codex, Copilot, Windsurf, Cline | Нативной загрузки нет | Попросить агента выполнить роль по `agents/_contract.md` и `agents/onec-*.md` в отдельной сессии |

Правило синхронизации: поле `description` в обоих адаптерах одного субагента совпадает. Харнесс выбирает субагента по описанию, поэтому расхождение приводит к тому, что в разных средах субагент вызывается в разных ситуациях.

## 4. Как вызывать

- **Автоматически.** Главный агент выбирает субагента по полю `description`, когда задача ему соответствует.
- **Явно в Cursor:** `/onec-reviewer проверь незакоммиченные изменения`.
- **Явно в любом харнессе:** «Запусти субагента onec-query-auditor для модуля ...».

### Шаблон задания

Субагент не видит переписки, поэтому задание составляется полностью:

```text
Цель: {один вопрос или одна проверка}
Объект работы: {пути | ветки <база>...<ветка> | незакоммиченные изменения | путь к worktree}
Ограничения: {что исключить и почему, например: запросы не проверять, их проверяет onec-query-auditor}
Контекст задачи: {требования и критерии приемки, если нужны для проверки}
```

Параметры проекта в задание не пересказываются: субагент читает `project-profile.md` сам.

## 5. Конвейеры

Субагенты не запускают других субагентов. Конвейер собирает главный агент: он запускает субагентов, принимает их отчеты и передает отчеты в `onec-verifier`.

### Конвейер А. Разведка перед доработкой

1. `onec-explorer` - карта механизма, который предстоит дорабатывать.
2. Главный агент сам открывает 2-3 ключевых места из карты, прежде чем проектировать изменение.
3. Если карта содержит динамические вызовы с неопределенной целью, главный агент сообщает об этом пользователю до начала доработки.

### Конвейер Б. Проверка перед коммитом

1. Параллельно, на незакоммиченных изменениях:
   - `onec-reviewer` с ограничением «запросы не проверять»;
   - `onec-query-auditor` - если в diff есть запросы;
   - `onec-metadata-validator` - если в diff есть `*.mdo` или `*.form`;
   - `onec-bsp-checker` - если `{USES_BSP} = Да` и в diff есть вызовы общих модулей.
2. `onec-verifier` - на все отчеты сразу, если в них есть CRITICAL или HIGH.
3. Главный агент:
   - объединяет замечания и убирает дубликаты;
   - исключает опровергнутые, неточные исправляет по вердикту;
   - показывает пользователю итог с вердиктами проверяющего;
   - вносит исправления только после согласия пользователя.

### Конвейер В. Ревью MR/PR

1. Главный агент готовит `{REVIEW_WORKTREE}` по `workflow/code-review.md`, раздел 1. Субагенты этого не делают: переключение веток меняет состояние.
2. Тот же параллельный набор, что в конвейере Б, с объектом работы `<целевая-ветка>...<ветка-MR>` и путем к worktree.
3. `onec-verifier` на все отчеты.
4. Главный агент публикует только подтвержденные замечания и только черновиками по `workflow/code-review.md`, раздел 3. Одобрение и слияние MR/PR запрещены.

## 6. Как главный агент принимает отчет

Перед использованием отчета главный агент проверяет:

1. **Статус.** `BLOCKED` - устранить причину и перезапустить. `PARTIAL` - решить, дозапускать ли проверку непокрытой части или сообщить о ней пользователю.
2. **Покрытие.** Прочитанные файлы и раздел «Что не проверено» вместе покрывают весь объект работы.
3. **Ссылки.** У каждого вывода есть ссылка `файл:строка`. Вывод без ссылки не используется.
4. **Противоречия.** Если отчеты двух субагентов расходятся в одном месте, главный агент открывает это место сам.

Отчет, не прошедший пункты 2 или 3, возвращается субагенту на доработку (повторный запуск с уточненным заданием) или передается в `onec-verifier`.

## 7. Как разработчику проверить работу субагента

- **Лог субагента.** В Cursor блок вызова субагента в чате раскрывается: видно задание, рассуждения, прочитанные файлы, запущенные команды и итоговый ответ. Полные стенограммы сохраняются в истории чатов проекта.
- **Выборочная проверка.** Ссылки `файл:строка` в отчете кликабельны: 2-3 замечания стоит открыть самому.
- **Вердикты проверяющего.** Итог конвейера показывает, какие замечания подтверждены по исходникам, а какие нет.

Признаки отчета, которому нельзя доверять:
- нет раздела «Что не проверено» или в нем «нет» при большом объеме проверки;
- «проблем не найдено» без перечня шаблонов поиска;
- цитаты кода не совпадают с файлом;
- замечания к стороннему коду;
- анализатор указан как запущенный, но в разделе «Команды и поиски» нет команды и ее результата.

## 8. Как добавить нового субагента

1. Убедиться, что задача проходит критерии раздела 1 и не дублирует существующего субагента.
2. Создать `agents/onec-<имя>.md` по образцу существующих: назначение, когда вызывать и когда не вызывать, вход, что прочитать, порядок работы, формат раздела «Выводы».
3. Создать адаптеры `.cursor/agents/onec-<имя>.md` и `.claude/agents/onec-<имя>.md` с одинаковым `description`. Если субагент пишет файлы, `readonly` в адаптере Cursor не ставить и явно описать в `agents/onec-<имя>.md`, в какие зоны он пишет.
4. Добавить строку в таблицу раздела 2 этого документа и в `AGENTS.md`.
