# Модуль workflow: командные процессы разработки 1С

Раздел описывает процессы совместной разработки: ветвление в Git, код-ревью Merge/Pull Request, диагностику BSL Language Server, ведение заметок и журнала работы.

В отличие от инвариантных правил кода 1С (`../rules/`), процессы зависят от используемого Git-хостинга, трекера задач, структуры репозитория и договоренностей команды.

Параметры разделены на два уровня:
1. **Общие параметры проекта** (в таблице ниже, коммитятся в репозиторий).
2. **Личные параметры разработчика и сопоставление инструментов** (в `workflow/local.md`, создается по шаблону `workflow/local.example.md` и не коммитится).

Если какой-то из параметров не задан, агент не должен придумывать его значение по умолчанию, а обязан запросить уточнение у пользователя.

---

## 1. Общие параметры проекта (коммитятся)

| Параметр | Что это | Где используется | Значение по умолчанию |
|---|---|---|---|
| `{ОСНОВНАЯ_ВЕТКА}` | Ветка, в которую сливаются текущие доработки (`develop`, `main`) | `git-workflow.md`, `code-review.md` | `develop` |
| `{РЕЛИЗНАЯ_ВЕТКА}` | Релизная ветка (если используется в модели ветвления) | `git-workflow.md` | **Не задана.** Уточнять целевую ветку у пользователя при создании хотфикса или релизного ревью |
| `{BRANCHING_STRATEGY}` | Стратегия ветвления (`gitflow`, `github-flow`, `trunk-based`) | `git-workflow.md` | `gitflow` |
| `{ПРЕФИКСЫ_ЗАДАЧ}` | Шаблоны ключей задач в трекере (`DEV-*`, `TASK-*` и т.п.) | `git-workflow.md`, `code-review.md`, `notes-artifacts.md` | `DEV-*`, `TS-*` |
| `{ПУТЬ_К_КОНФИГУ_BSLLS}` | Путь к конфигурационному файлу BSL Language Server | `bsl-mcp.md` | `.bsl-language-server.json` в корне репозитория |

---

## 2. Личные параметры разработчика (не коммитятся)

Каждый разработчик настраивает собственное окружение в файле `workflow/local.md` (файл находится в `.gitignore`, шаблон для копирования - `workflow/local.example.md`):

| Параметр | Назначение |
|---|---|
| `{РАБОЧАЯ_КОПИЯ}` | Путь к основному рабочему каталогу репозитория, где ведется разработка |
| `{REVIEW_WORKTREE}` | Путь к отдельному изолированному git worktree для проведения ревью MR/PR |
| `{GIT_PROVIDER}` | Провайдер Git-хостинга (`gitlab`, `github`, `local`) |
| `{GIT_PROJECT_ID}` | Идентификатор проекта на хостинге (`group/project` или `owner/repo`) |
| `{TASK_PROVIDER}` | Система трекера задач (`jira`, `youtrack`, `kaiten`, `github`, `manual`) |
| `{NOTES_STORAGE}` | Путь к хранилищу заметок (`obsidian`, локальная папка `./docs/notes` или `none`) |

Правила для агента:
- Значения путей и параметров окружения считывать из `workflow/local.md`.
- Без `{REVIEW_WORKTREE}` ветку для ревью в основную рабочую копию `{РАБОЧАЯ_КОПИЯ}` не выкачивать, чтобы не затереть локальные незакоммиченные файлы.
- Без указания хранилища заметок (`{NOTES_STORAGE} = none` или пусто) заметки на диск не сохранять, выводя резюме прямо в диалог.
- Файл `workflow/local.md` ни при каких обстоятельствах не коммитить и не включать в PR/MR.

## 3. Концепция Capability-based MCP Tooling

Правила и скиллы не привязываются жестко к названиям конкретных MCP-плагинов (`user-gitlab`, `user-jira`, `user-bsl-mcp`). Вместо этого взаимодействие строится через функциональные роли (capabilities):

| Функциональная роль | Назначение | Возможные реализации | Поведение при отсутствии |
|---|---|---|---|
| `bsl-diagnostics` | Статический анализ BSL/OS, синтакс-контроль, валидация правил | MCP BSL Language Server (`analyze_file`), CLI `bsl-language-server`, платформенный синтакс-контроль 1С | Проводится ручная сверка со стандартами `../rules/`. В отчете явно отмечается отсутствие инструмента |
| `metadata-provider` | Чтение состава объектов метаданных, реквизитов, типов и форм | Чтение файлов EDT (`*.mdo`, `Configuration.mdo`) по пути `{EDT_PROJECT_FORMAT}`, MCP-сервер метаданных 1С | Поиск по структуре каталогов и файлам метаданных через инструменты Grep, Glob, Read |
| `platform-docs` | Справка по типам и методам платформы 1С, стандартам БСП | Встроенные знания модели, справочные правила проекта, MCP-сервер документации 1С | Проверка по официальной документации ИТС и правилам `../rules/` с учетом `{PLATFORM_VERSION}` |
| `git-host` | Получение MR/PR, diff изменений, комментирование строк | GitLab MCP / API, GitHub CLI (`gh`) / MCP, локальный Git (`git diff`) | Работа через локальные команды Git, вывод сводного отчета ревью в markdown |
| `task-tracker` | Получение описания задачи, критериев приемки и комментариев | Jira MCP / API, YouTrack MCP, Kaiten MCP, GitHub Issues, ручной ввод в диалоге | Требования берутся непосредственно из текста запроса пользователя (`manual`) |

При начале работы агент сверяет доступные в текущей сессии инструменты (`GetDynamicTools`) с картой ролей из `workflow/local.md`.

## 4. Что внутри каталога

| Файл | О чем |
|---|---|
| `git-workflow.md` | Стратегии ветвления (GitFlow, GitHub Flow, trunk-based), границы задачи, правила именования веток, запреты на прямой push |
| `code-review.md` | Регламент код-ревью MR/PR: получение diff, проверка требований задачи, запуск BSL LS, ручной аудит по стандартам, публикация черновиков |
| `bsl-mcp.md` | Настройка и запуск BSL Language Server через MCP или CLI, правила фильтрации диагностик, работа с исключениями |
| `notes-artifacts.md` | Фиксация артефактов: анализ задачи (`analyse/`), единый журнал сессий (`worklog/`), архитектурные решения (`Architecture/` ADR) |

---

## 5. Границы применения проверок

Замечания статического анализа и код-ревью не выставляются по сторонним зонам репозитория (библиотечный код вендоров, фреймворки автотестирования, неизменяемый типовой код конфигурации). Разграничение зон кода описано в `../rules/project-context.md`.
