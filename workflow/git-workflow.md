# Область работы и процесс работы с Git

Документ описывает регламент работы с репозиторием Git: границы задачи, поддерживаемые модели ветвления, правила именования веток и защитные ограничения.

Параметры окружения берутся из `workflow/README.md` (общие) и `workflow/local.md` (личные настройки разработчика).

---

## 1. Границы задачи и область рассмотрения

Разработка всегда ведется в контексте конкретной задачи трекера:

- По умолчанию анализировать и изменять только те объекты метаданных и модули, которые непосредственно относятся к задаче (определены в описании тикета, критериях приемки или выявлены на этапе анализа).
- Не распространять правки на соседние несвязанные подсистемы и не проводить попутный рефакторинг без явной команды пользователя.
- Ключи задач определяются шаблонами из `{ПРЕФИКСЫ_ЗАДАЧ}` (например, `DEV-*`, `TASK-*`).
- **Исключение для ревью:** при код-ревью MR/PR область рассмотрения шире: анализируется весь diff изменений целиком (см. `code-review.md`).

## 2. Стратегии ветвления (`{BRANCHING_STRATEGY}`)

Проект может использовать одну из трех распространенных моделей ветвления:

### Вариант A. GitFlow (`BRANCHING_STRATEGY = gitflow`)

- **Основная ветка разработки:** `{ОСНОВНАЯ_ВЕТКА}` (обычно `develop`). В нее сливаются готовые доработки через MR/PR.
- **Релизная ветка:** `{РЕЛИЗНАЯ_ВЕТКА}` (например, `main`, `master` или `release/vX.Y`). Содержит стабильный код производственного контура.
- **Ветки доработок:**
  - `feature/{КЛЮЧ_ЗАДАЧИ}-<описание>`: новая функциональность, ответвляется от `{ОСНОВНАЯ_ВЕТКА}` и сливается обратно в нее.
  - `bugfix/{КЛЮЧ_ЗАДАЧИ}-<описание>`: исправление ошибок текущего спринта, ответвляется от `{ОСНОВНАЯ_ВЕТКА}`.
- **Хотфиксы:** `hotfix/{КЛЮЧ_ЗАДАЧИ}-<описание>`: срочные исправления продуктовой базы. Ответвляются от `{РЕЛИЗНАЯ_ВЕТКА}` и вливаются в `{РЕЛИЗНАЯ_ВЕТКА}` и `{ОСНОВНАЯ_ВЕТКА}` (или переносятся cherry-pick по согласованию).

### Вариант B. GitHub Flow / GitLab Flow (`BRANCHING_STRATEGY = github-flow`)

- **Основная ветка:** `{ОСНОВНАЯ_ВЕТКА}` (обычно `main` или `master`), всегда готова к релизу.
- **Ветки доработок:** создаются напрямую от `{ОСНОВНАЯ_ВЕТКА}` под каждую задачу:
  `feature/{КЛЮЧ_ЗАДАЧИ}-<описание>` или `fix/{КЛЮЧ_ЗАДАЧИ}-<описание>`.
- Слияние выполняется через Pull Request / Merge Request после обязательного прохождения автотестов и код-ревью.

### Вариант C. Trunk-Based Development (`BRANCHING_STRATEGY = trunk-based`)

- Разработка ведется в короткоживущих ветках (жизненный цикл 1-2 дня), ответвляемых от `{ОСНОВНАЯ_ВЕТКА}` (`main`).
- Незавершенный функционал изолируется с помощью функциональных переключателей (Feature Flags / Константы 1С / функциональные опции), а не долгоживущими ветками.

## 3. Правила именования веток

- Формат: `<тип>/<ключ-задачи>-<краткий-слаг>`
  - Примеры: `feature/DEV-1240-bonus-calc`, `bugfix/TS-890-null-pointer`, `hotfix/DEV-1300-vat-rate`.
- Регистр ключа задачи: согласовывать с традициями проекта и трекера (например, `DEV-123` или `dev-123`). Если ветка уже создана пользователем, использовать ее точное имя.
- Перед созданием новой ветки проверить `git branch -a` и `git ls-remote`: ветка под задачу может быть уже заведена пользователем в EDT или IDE.

---

## 4. Взаимодействие с Git-хостингом (роль `git-host`)

В зависимости от значения `{GIT_PROVIDER}` в `workflow/local.md`:

- **`gitlab`:** создание Merge Request в целевую ветку (`{ОСНОВНАЯ_ВЕТКА}`), отслеживание пайплайнов GitLab CI, ревью через draft notes.
- **`github`:** создание Pull Request через GitHub CLI (`gh pr create`) или интерфейс хостинга, отслеживание GitHub Actions.
- **`local`:** работа без удаленного API хостинга: подготовка ветки, локальный diff, передача изменений через патчи или локальный merge по указанию пользователя.

---

## 5. Защитные правила и строгие запреты

1. **Никогда не пушить напрямую** в защищенные ветки (`{ОСНОВНАЯ_ВЕТКА}`, `{РЕЛИЗНАЯ_ВЕТКА}`). Все изменения в эти ветки попадают исключительно через MR/PR после ревью.
2. **Запрещен жесткий `git push --force`** без явного разрешения пользователя. Допустим только `--force-with-lease` при актуализации собственной feature-ветки (rebase) после предварительного подтверждения.
3. **Не переключать ветки** в основной рабочей копии `{РАБОЧАЯ_КОПИЯ}` без явного запроса пользователя: там могут находиться незакоммиченные файлы или несохраненные конфигурации 1C:EDT.
4. **Ревью чужих веток** проводить строго в изолированном каталоге `{REVIEW_WORKTREE}` (см. `code-review.md`).
