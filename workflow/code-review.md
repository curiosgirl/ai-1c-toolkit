# Регламент код-ревью Merge Request и Pull Request

Документ определяет единый процесс проведения код-ревью в проектах 1С.

Параметры окружения берутся из `workflow/README.md` (общие) и `workflow/local.md` (личные настройки разработчика и сопоставление ролей MCP).

Триггер: пользователь запрашивает проверку MR/PR (номер тикета, ссылка на MR/PR или имя ветки).

В отличие от обычной разработки по задаче, код-ревью **не ограничивается** узким описанием тикета: анализируется **весь diff изменений целиком**.

Правила стандартов BSL, с которыми сверяется diff, находятся в каталоге `../rules/` (индекс - `../rules/coding-standards.md`). Перед проверкой агент читает релевантные правила, а не полагается на память.

---

## 1. Изолированная рабочая копия для ревью (git worktree)

Ветку MR/PR для проведения ревью **запрещено выкачивать** в основную рабочую копию `{РАБОЧАЯ_КОПИЯ}`: там идет активная разработка пользователя и могут быть незакоммиченные файлы.

Вместо этого используется отдельный каталог git worktree по **фиксированному пути** `{REVIEW_WORKTREE}`.

**Зачем путь worktree должен быть фиксированным:**
BSL Language Server при первом вызове анализа индексирует корень конфигурации (1-2 минуты). Если выкачивать каждую ветку в новый временный каталог, индекс будет перестраиваться заново. При постоянном пути `{REVIEW_WORKTREE}` индекс и кэш остаются прогретыми между ревью разных задач.

### Команды подготовки worktree

Перед ревью конкретной ветки:

```bash
cd {РАБОЧАЯ_КОПИЯ}
git fetch origin
cd {REVIEW_WORKTREE}
git checkout -B <имя-ветки-MR> origin/<имя-ветки-MR>
```

Если каталог `{REVIEW_WORKTREE}` еще не создан:

```bash
git -C {РАБОЧАЯ_КОПИЯ} worktree add --detach {REVIEW_WORKTREE} origin/{ОСНОВНАЯ_ВЕТКА}
```

Команда `git checkout -B ... origin/...` безопасно перезаписывает ветку в worktree состоянием из удаленного репозитория. В каталоге `{REVIEW_WORKTREE}` разработка не ведется, поэтому потеря локальных данных исключена. Все последующие операции чтения файлов и вызовы статического анализа выполняются по путям внутри `{REVIEW_WORKTREE}`.

## 2. Пошаговый порядок проведения ревью

### Шаг 1. Получение информации об изменениях (роль `git-host`)

В зависимости от `{GIT_PROVIDER}`:
- **GitLab:** получение данных через MCP-сервер или API хостинга (`get_merge_request`, `list_merge_request_changed_files`, `get_merge_request_diffs`). Идентификатор проекта берется из `{GIT_PROJECT_ID}`.
- **GitHub:** получение данных через GitHub CLI (`gh pr view`, `gh pr diff`) или GitHub MCP.
- **Локальный Git (`local`):** получение списка файлов и diff через консольные команды:
  `git diff origin/{ОСНОВНАЯ_ВЕТКА}...HEAD` или `git diff <целевая-ветка>...<ветка-MR>`.

### Шаг 2. Сверка с требованиями задачи (роль `task-tracker`)

По ключу задачи из названия ветки или заголовка MR (`{ПРЕФИКСЫ_ЗАДАЧ}`):
- Получить описание тикета, критерии приемки и последние комментарии (через Jira MCP, YouTrack MCP, Kaiten MCP, GitHub Issues или из вводного текста пользователя).
- Сверить: решает ли код в MR поставленную бизнесом задачу? Нет ли нереализованных критериев приемки или избыточных доработок, не относящихся к тикету?
- Несоответствия исходной постановке выносятся в замечания общего уровня к MR.

### Шаг 3. Автоматическая диагностика (роль `bsl-diagnostics`)

Если BSL Language Server или линтер доступны в сессии (см. `bsl-mcp.md`):
- Для каждого измененного файла `*.bsl` / `*.os` запустить анализ файла по его абсолютному пути внутри `{REVIEW_WORKTREE}`.
- Сопоставить полученные диагностики со строками diff:
  - Учитывать только срабатывания на измененных или добавленных строках, либо ошибки, вызванные внесенной правкой.
  - Ошибки в сторонних зонах (библиотеки вендоров, движки тестов по `../rules/project-context.md`) замечаниями к MR не считаются.
  - Классификация: `Error/Warning` -> статус `[blocking]`, `Information/Hint` -> статус `[nit]`.
- Если автоматический анализатор недоступен: не останавливать ревью, выполнить ручную проверку и явно зафиксировать в отчете отсутствие инструмента автоматической диагностики.

### Шаг 4. Построчная сверка со стандартами разработки 1С

Для измененных модулей открыть файлы правил `../rules/` и проверить:
- **Запрещенные конструкции (`../rules/code-style.md`):** отсутствие тернарного оператора `?(...)`, `Выполнить()` / `Вычислить()`, `Сообщить()`, сравнений с `Истина`/`Ложь`, Yoda-синтаксиса, буквы е с двумя точками, дефисов вместо длинных тире.
- **Именование и структура (`../rules/code-style.md`, `../rules/module-structure.md`):** канонические области `#Область`, отсутствие вложенных областей внутри процедур, понятные имена переменных без венгерской нотации и коллизий с глобальным контекстом.
- **Работа со ссылочными данными (`../rules/architecture.md`):** запрет обращения через точку от ссылок на сервере при наличии БСП (использовать `ОбщегоНазначения.ЗначениеРеквизитаОбъекта*`).

### Шаг 5. Корректность бизнес-логики и транзакций

- **Транзакции и блокировки (`../rules/locks-and-transactions.md`):** явная установка управляемых блокировок перед записью наборов регистров при `LOCK_MODE = Managed`, минимальная длительность транзакций, отсутствие вызовов клиентских методов и длительных операций внутри транзакции.
- **Граничные условия:** обработка значений `Null`, `Неопределено`, пустых ссылок, пустых выборок запроса.
- **Интеграция с БСП:** корректное использование длительных операций, механизмов фоновых заданий, подсистемы версионирования.

### Шаг 6. Производительность запросов (`../rules/query-design.md`)

- Отсутствие запросов внутри циклов (антипаттерн №1).
- Установка параметров виртуальных таблиц в самих таблицах, а не в секции `ГДЕ`.
- Применение временных таблиц с индексацией вместо тяжелых подзапросов в соединениях.
- Отсутствие избыточных `РАЗЛИЧНЫЕ` и обращений через две точки в полях выборки.

## 3. Публикация результатов ревью

Порядок публикации замечаний зависит от `{GIT_PROVIDER}`:

### Вариант A. GitLab (`GIT_PROVIDER = gitlab`)

- Публикация замечаний выполняется **строго в режиме черновиков** (`create_draft_note`).
- Прямая публикация комментариев (`create_merge_request_note`) и немедленная публикация всех черновиков (`bulk_publish_draft_notes`) запрещены.
- Пользователь просматривает созданные агентом черновики в веб-интерфейсе GitLab и лично принимает решение об их публикации.
- Точные параметры привязки к строке берутся из `diff_refs` MR (`base_sha`, `head_sha`, `start_sha`, `position_type: "text"`).

### Вариант B. GitHub (`GIT_PROVIDER = github`)

- Публикация замечаний выполняется в режиме pending review (черновик проверки) через GitHub API / CLI:
  `gh pr review <номер> --comment -b "Текст"` или через формирование черновика ревью.
- Окончательную отправку ревью (Submit review) выполняет разработчик через веб-интерфейс GitHub.

### Вариант C. Локальный или универсальный режим (`GIT_PROVIDER = local` или отсутствие MCP)

- Агент формирует единый структурированный сводный отчет ревью в формате Markdown прямо в диалоге или записывает его в файл (например, `docs/reviews/MR-<номер>.md`).
- Отчет содержит разбивку по файлам, точные номера строк, сниппеты кода, уровень критичности и пояснения, почему конструкция требует исправления.

### Строгий запрет на автоматическое одобрение и слияние

**Агенту категорически запрещено автоматически одобрять (Approve) или сливать (Merge) MR/PR.**
Принятие решения о прохождении ревью и слиянии ветки является исключительной прерогативой разработчика.

## 4. Итоговое резюме в диалоге

После завершения ревью агент формирует в диалоге краткое резюме:
1. **Статистика замечаний:** общее количество, разбивка на `[blocking]` и `[nit]`, список проверенных файлов.
2. **Результат автоматической диагностики:** запускался ли BSL LS, количество выявленных им проблем или причина, по которой запуск не производился.
3. **Сверка с задачей:** соответствует ли реализация бизнес-требованиям тикета в трекере.
4. **Главные риски:** критические уязвимости производительности, блокировок или потенциальные падения в рантайме.
