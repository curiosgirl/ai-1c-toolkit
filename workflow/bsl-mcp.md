# BSL Language Server и диагностика BSL-кода

Файл регламентирует выполнение автоматической диагностики кода на языке 1С (BSL) и OneScript (OS). В архитектуре инструментов эта функциональность относится к роли `bsl-diagnostics`.

Диагностика может выполняться двумя основными способами:
1. **Через MCP-сервер** (встроенный MCP в JAR BSL Language Server или MCP-адаптер).
2. **Через консольный запуск CLI** (запуск `bsl-language-server` из командной строки).

Если инструменты автоматического анализа в среде отсутствуют, агент проводит ручную сверку кода по стандартам `../rules/` и обязательно отмечает в отчете, что автоматическая проверка не выполнялась.

---

## 1. Конфигурация BSL Language Server

- Основной конфигурационный файл: `{ПУТЬ_К_КОНФИГУ_BSLLS}` (по умолчанию `.bsl-language-server.json` в корне репозитория).
- **Исключения сторонних зон:** через секцию `subsystemsFilter.exclude` или `excludePaths` из анализа исключаются сторонние библиотеки вендоров и движки тестирования, определенные в `../rules/project-context.md`. Срабатывания линтера в этих файлах не считаются дефектами текущей задачи.
- **Исключения синтакс-контроля:** специфичные файлы исключений платформенного синтакс-контроля (например, `tools/syntax-check/exceptionFile.txt`) содержат известные платформенные особенности (вызовы внешних компонент, специфика COM-соединений). Ложные срабатывания на этих конструкциях фильтруются.
- **Учет версий и режимов совместимости:** общая конфигурация ориентируется на версию платформы `{PLATFORM_VERSION}` из `../project-profile.md`. Если проверяемый модуль находится в расширении с собственным пониженным режимом совместимости (см. `../rules/project-context.md`), диагностики, зависящие от версии платформы, должны оцениваться с учетом ограничений этого расширения.

## 2. Использование через MCP (`bsl-diagnostics`)

В настройках агента инструмент роли `bsl-diagnostics` обычно представлен сервером `user-bsl-mcp` (или аналогичным именем из `workflow/local.md`).

### Состав инструментов

- `analyze_file` (основной): принимает абсолютный путь к файлу `.bsl` или `.os` и возвращает список диагностик с номерами строк, кодами правил, сообщениями и уровнем важности (Severity).
- Вспомогательные инструменты навигации: `definition`, `find_references`, `document_symbols`, `type_info`, `call_hierarchy`.

### Порядок вызова

1. Определить имя инструмента в текущей сессии через `GetDynamicTools` по карте ролей из `workflow/local.md`.
2. Вызывать анализ файла с **абсолютным путем** на диске. При ревью MR/PR вызывать анализ по путям внутри изолированного `{REVIEW_WORKTREE}`.
3. **Особенность первого запуска:** при первом вызове анализа BSL Language Server выполняет индексацию проекта по корню конфигурации. Для конфигураций уровня ERP/КА/УТ этот процесс может занимать до 1-2 минут. Это штатное поведение, операцию нельзя обрывать по таймауту.
4. При последующих вызовах в том же рабочем каталоге кэш остается прогретым, и проверка одного файла выполняется за доли секунды.

## 3. Использование через консольный CLI

Если MCP-сервер BSL Language Server не подключен, но в системе установлен исполняемый файл или JAR-пакет BSL LS, проверку можно запустить через терминал.

### Варианты запуска

1. **Через установленный бинарный пакет:**
   ```bash
   bsl-language-server analyze -c .bsl-language-server.json --src <путь-к-файлу-или-каталогу>
   ```

2. **Через Java JAR-пакет:**
   ```bash
   java -jar <путь-к-bsl-language-server.jar> analyze -c .bsl-language-server.json -s <путь-к-файлу>
   ```

3. **Синтакс-контроль средствами платформы 1С:**
   При наличии специализированных скриптов проекта (например, через `v8runner` или EDT CLI) синтакс-контроль выполняется вызовом штатной команды проекта:
   ```bash
   v8runner syntax-check --ibconnection <параметры>
   ```

## 4. Правила фильтрации и классификации диагностик

При разработке и код-ревью агент обязан соблюдать правила отбора замечаний:

1. **Фильтрация по diff:** интерес представляют только те диагностики, которые попадают в измененные строки или непосредственно вызваны изменениями текущей задачи. Ошибки в неизмененных участках унаследованного кода фиксировать в рамках текущего ревью запрещено (чтобы не загромождать контекст).
2. **Градация критичности:**
   - `severity: Error` или `Warning` транслируются в статус `[blocking]`. Это критичные ошибки, ломающие выполнение, приводящие к утечкам ресурсов, блокировкам или нарушениям ключевых стандартов.
   - `severity: Information` или `Hint` транслируются в статус `[nit]`. Это рекомендации по улучшению читаемости или мелкие стилистические правки.
3. **Игнорирование сторонних зон:** если файл относится к присоединенным библиотекам или движку автотестов (согласно `../rules/project-context.md`), замечания BSL LS не формируются.

---

## 5. Границы применимости автоматической диагностики

BSL Language Server является эффективным первичным ситом, но не заменяет ручную сверку по `../rules/`:
- BSL LS может не контролировать чтение реквизитов через точку при наличии БСП (требование проекта: использовать `ОбщегоНазначения.ЗначениеРеквизитаОбъекта*`).
- BSL LS не оценивает оптимальность структуры запросов и использование временных таблиц в сложных выборках.
- BSL LS не проверяет достаточность управляемых блокировок перед записью регистров.
- BSL LS не проверяет смысловую корректность бизнес-логики и соответствие постановке задачи.

Автоматическая диагностика всегда дополняется архитектурной сверкой по `../rules/coding-standards.md`.
